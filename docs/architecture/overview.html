Stakeholder Executive summary

CueClose helps a tour finance desk keep books current while shows move city to city. Invoices arrive as ambient cues with source evidence. The product recommends an account and show. A person with the right role approves. Only then does CueClose post a balanced journal. Reconciliation never silently rewrites amounts; it explains variance against a legacy snapshot.

Trust

Authority is explicit

Role, materiality, and confidence gates run on the server. Channel messages cannot grant approval power.

Accuracy

Money stays exact

Amounts are decimal strings on the wire and exact decimal math in domain code. No binary float for money.

Accountability

Every action leaves a trail

Reviews, approvals, posts, and variance explanations append audit events with actor, reason, and policy version.

One-line product promise

A model may recommend. It never posts. Humans decide under policy. The ledger stays balanced and explainable.

Engineer Data model

Core entities live in the Python domain package and are mirrored in the Next.js demo store. Amounts travel as decimal strings. Cue status is a closed set of workflow states.

Recommendation Advisory only Account, show, confidence, rationale, evidence ids, policy notes. Never posts.

Policy failures return HTTP 403 with a stable code such as MATERIALITY, LOW-CONFIDENCE, HOLD-ESCALATION, or E-01-ROLE. Invalid state transitions return 409. Ledger invariant failures return 422.

Engineer Auth and session

Viewer binding

Private or Team publishes resolve a signed-in Cursor identity. Public publishes fall back to an HttpOnly guest cookie (cueclose_vid). Demo personas are bound server-side to that viewer. The browser never sends an actor id to authorize a decision.

Default personas

Guests start as Jordan Blake (production manager). Signed-in viewers can act as Maya Chen (tour controller) for material approvals and reset. Role labels are product fiction for the Horizon Arena Tour demo.

Authority boundary

Channel excerpts are evidence, not credentials. Only the server-side policy engine grants or denies write paths.

Engineer Edition gating and Pro desks

Edition cookie and header

Edition is selected in the header and persisted via cueclose_edition. API handlers also honor x-cueclose-edition. Parsing treats legacy baseline as Classic; default is Pro. Implementation: web/src/lib/edition.ts.

Waiting-on-me queue

waitingOnMe(store, actor) filters open cues by role. Tour controllers see material, held, low-confidence, and awaiting-approval work. Production managers see only cues they can legally decide. Tour managers see held or unassigned show cues. Command surfaces the queue; the inbox can filter with ?waiting=1.

Show filters

Pro inbox adds a show/venue select that filters on suggested_show_id. Classic hides the Pro-only near-duplicate seed cue (cue_006) so the core story stays clean.

Duplicate acknowledge gate

findDuplicateCandidates looks for same vendor, amount within 5%, received within 14 days, plus optional similar invoice number and same suggested show. Match reasons are returned on cue detail in Pro. Approvals require acknowledge_duplicate: true when candidates exist; otherwise the API rejects with a clear warning payload. The UI keeps Approve disabled until the checkbox is checked.

Tradeoffs

Choice Benefit Cost / follow-on
Modular monolith Clear transactions, one deploy story for the reference API Later extraction only when measured need appears
Seeded process memory Instant demo, deterministic tests, no database ops Restart clears mutations unless Reset demo reseeds
Embedded Next.js API One-process UI demo for stakeholders Python service remains the exact-decimal test spine
Explain-only reconciliation No silent book rewrites; audit-friendly Operators must still resolve books elsewhere
Heuristic duplicate gate Catches resent invoices before double post Not identity resolution; false positives need acknowledge
Edition toggle in-product Side-by-side Classic vs Pro storytelling Feature flags are demo-scoped, not multi-tenant SKUs yet
